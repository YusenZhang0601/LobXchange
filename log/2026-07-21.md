### 1. 50,000 笔高频订单基线压测结果 (Baseline Benchmark)

在未改动原始代码的前提下，运行 50,000 笔高频订单压力测试，测量数据如下：
- **吞吐量 (TPS)**：平均仅 **1,000 ~ 2,188 笔/秒**（远低于正常 C++ 纯内存撮合引擎 1,000,000+ TPS 的标准）。
- **延迟分布**：P50 83~947 μs，P95 780~1,757 μs，P99 1.85~2.05 ms。
- **最大单笔延迟 (Max Latency)**：飙升至 **36.7ms ~ 110.75ms**（单笔订单延迟超过 1/10 秒！）。
- **瓶颈诊断**：随着盘口挂单数量 $N$ 增加，`MarketEngine::submit_limit` 入口处的 `make_submit_snapshot()` 每次均全量遍历买卖盘口、OpenOrders 表、Ledger 与 PositionEngine 并进行深拷贝，造成了严重的内存分配抖动与 $O(N)$ 复杂度退化。

### 2. 深度梳理出的 10 项技术债清单

1. **核心撮合热路径 $O(N)$ 全量快照深拷贝 (`make_submit_snapshot`)**：每笔限价单入口处无条件全量深拷贝，导致吞吐量崩溃与尾部延迟飙升至 110ms。拟重构为基于轻量级 Undo Log 的增量回滚。
2. **Subprocess JSON IPC 管道通信瓶颈 (`mesa_exchange.py`)**：Python 与 C++ 依赖 `subprocess.Popen` + `stdin`/`stdout` 文本 JSON 序列化，高频交互开销极大。拟重构为 Pybind11 / C-API 动态库直连。
3. **多线程并发安全性完全缺失 (Lack of Thread Safety)**：`Exchange` 与 `MarketEngine` 全无锁设计，并发调用引发 Data Race。拟引入细粒度读写锁。
4. **关键清算溢出错误静默吞没 (`PositionEngine::apply_trade`)**：`(void)apply_trade_checked(...)` 强行忽略溢出返回值，导致数据破坏。拟妥善传递错误与 RejectCode。
5. **历史成交与 K 线 Vector 无界积聚**：`trade_history_` 与 `candle_history_` 未在内部限制容量，长周期仿真引发伪内存泄漏。拟增加容量上限与环形覆盖机制。
6. **热路径字符串 Hash 查找开销**：`submit_limit` 等入参使用字符串 Hash 查找引擎。拟在初始化阶段映射为整数 `MarketId` 句柄。
7. **持仓均价浮点数强转舍入误差 (`long double` Casting)**：`apply_trade_checked` 使用 `long double` 可能产生跨平台 1 Tick 偏差。拟改用 128 位整数 (`__int128_t`) 定点计算。
8. **数据结构嵌套与 CPU Cache 连续性破坏**：`AccountLedger` 与 `PositionEngine` 使用双层 `unordered_map`。拟重构为一维平坦数组或对象池。
9. **日志与事件格式化开销 (`std::ostringstream`)**：在热路径拼接 Key-Value 字符串。拟重构为预分配字符 Buffer 或 FlatBuffers。
10. **Python 生态 Agent 决策逻辑占位 (Skeleton Placeholders)**：`GridBotAgent` 等策略 Agent `step()` 为 `pass`。拟分批补全策略 logic。
